# V1.1 部署、接入与人工安全验收

根据发布负责人提供的真实环境验收结果，VLESS + Reality 公网 TCP 443、多用户 add/disable/enable/delete、VPNGate Kill Switch、VPN 断线 fail-closed、自动重连换节点、Docker 服务重启恢复及端口边界均已通过。本次发布收尾仅执行离线验证，不重复运行验收；宿主整机重启、Mihomo 等未明确提供的结果不扩大认定。

本页运维命令供管理员在维护窗口执行，本次收尾不执行 Docker 或操作运行中的容器，不读取 secrets，不影响 TG Codex Agent。

正式 Xray 必须锁定 **26.3.27**（linux/amd64）：
`ghcr.io/xtls/xray-core@sha256:592ec4d11f656db95598d01e76dbcc6e002d67360b96a5436500a938230f52c7`。
详见 [兼容版本审计](Xray兼容版本审计.md)。

Reality target/SNI 必须在部署时显式配置，并先做 TLS 1.3 兼容性验证；`REALITY_TARGET` 必须与 `secrets/ingress.json` 中 ingress state 的 `sni` 一致。`www.apple.com` 是本次经真实 Shadowrocket 验证可用的示例，不是默认值或永久兼容保证。此前 Microsoft target 在当前 Xray 26.3.27 + REALITY 实现中出现 TLS record length 超过 8192 的兼容问题；不能据此认定 Microsoft 普遍不兼容。

V1.1 当前只支持 **TCP ingress**，所有客户端关闭 UDP forwarding；不开放 UDP 443。

## 1. 预备与安全存储

1. 在项目根目录运行 `bash scripts/verify.sh`。检查公开文件差异，不打包整个目录；不要提交 secrets、runtime、.test-work、.env、reference。当前目录没有 Git 元数据，首次导入时人工核对暂存文件。旧 After-Snapshot 不是本版清单。
2. 记录已有 VPN 镜像 ID、Compose、卷兼容性及恢复方案；原有 VPN 数据卷继续使用，不删除。记录 Docker/Compose、Linux、nft、Xray、Shadowrocket、Clash Verge/Mihomo 版本。本方案以普通 rootful Docker、无 userns-remap 为基线；rootless/UID 重映射未验证，可能使 skuid 65532 与实际 UID 不一致，不得未经重新设计和抓包验收直接采用。
3. Xray 只允许正式版 26.3.27，Compose 与锁文件已固定 root 核验的精确 RepoDigest，见 [兼容版本审计](Xray兼容版本审计.md)。必须先通过 `python3 scripts/check_xray_pin.py`；检查不再接受 pending 或其它 digest。`XRAY_IMAGE` 已停用，禁止 tag-only/latest。验证二进制路径 `/usr/local/bin/xray` 及 target/TCP Reality/Vision/SOCKS5 支持；VPN 的 Debian/APT 仍沿用 V1.0，依赖未完全锁定。
4. 部署时显式选择可经 VPNGate 访问的目标域名，先验证 TLS 1.3、SNI 证书和 ALPN，再使用锁定的 Xray 与实际客户端验证 Reality 握手和业务。普通 TLS 1.3 握手成功不能单独证明 REALITY record 长度兼容。不采用可滥用为广泛转发服务的 CDN 目标。目标只能为域名、固定 443，转发器不接受用户指定目的地址。目标 DNS 也经 tun。
5. 现有 `secrets/credentials.json` 保持原样，本次工具不自动轮换它。首次 V1 安装才用原有 `scripts/configure_credentials.py` 交互创建。部署时秘密由管理员持有，目录 0700、文件 0600；不通过参数、环境变量或终端输出传递秘密。
6. 以下环境变量只有非敏感部署参数，不需要真实 .env。用密码管理器/离线加密备份保管生成文件。Compose 本地 secret 和 bind mount 不是加密存储。

```bash
python3 scripts/check_xray_pin.py || exit 1
export REALITY_TARGET='REPLACE_WITH_REVIEWED_TLS13_HOSTNAME'
```

本版固定公网 TCP 443。若冲突，先解决部署设计，不任意改映射：导出端口、Compose 发布和验收必须一致。只发布 IPv4 443，IPv6 公网接入暂不支持。现有 SSH 端口照旧，无新增管理端口。

## 2. 首次生成和部署（管理员人工执行）

`init` 使用本地 OpenSSL X25519 实现，输出捕获在内存中，不自制椭圆曲线算法，不把私钥放 argv。需要管理员环境已有 OpenSSL。执行前关闭 shell tracing/录屏；不把导出结果贴入聊天。

```bash
python3 scripts/ingress_users.py init --host YOUR_SERVER_PUBLIC_IPV4 --sni "$REALITY_TARGET"
python3 scripts/ingress_users.py add alice
python3 scripts/ingress_users.py add bob
python3 scripts/ingress_users.py render
python3 scripts/ingress_users.py export alice
python3 scripts/ingress_users.py export bob
```

`init` 拒绝覆盖；用户 UUID/short ID 各自随机。`render` 由部署管理员执行，因为要给 `runtime/ingress` 设置 GID 65532 和文件 0640；父目录 runtime 为 0700。绑定整个目录使原子替换可见，不绑定单个文件。容器只读取服务器运行配置，不挂载用户数据库、其他用户导出或管理凭据文件。生成的 server.json 含内部代理认证及 Reality 私钥，亦属于秘密。GID 65532 不应赋给宿主普通用户。禁止通过放宽为 0777/0644 排错。

先在项目内创建空 `.test-work/empty.env`（不得复制真实 .env），再静态解析 Compose；不要将完整渲染配置打印或上传。以下命令均需管理员批准后执行：

```bash
COMPOSE_DISABLE_ENV_FILE=1 docker compose --env-file .test-work/empty.env -f compose.yaml -f compose.v1.1.yaml config --quiet
docker compose -f compose.yaml -f compose.v1.1.yaml build vpn
docker compose -f compose.yaml -f compose.v1.1.yaml up -d vpn
docker compose -f compose.yaml -f compose.v1.1.yaml run --rm --no-deps ingress run -test -config /run/ingress/server.json >/dev/null 2>&1
docker compose -f compose.yaml -f compose.v1.1.yaml up -d ingress
```

配置校验退出码必须为 0，失败时停止，不继续启动；确认 test 运行于正确 UID/无 capability。Xray 实际解析测试未在开发环境执行。可用临时无秘密测试配置在受控终端排错，禁止输出真实 server.json。默认 Xray 日志关闭，避免异常/访问日志泄漏；这也降低在线诊断能力。

Compose 启动依赖 VPN healthy，用于初始可用性；安全依赖内核与 socket 校验，**不依赖 Docker 持续处理 health**。VPN entrypoint 先装全阻断业务规则和 UID 边界再启动服务，安装/读回不符即退出。Docker 重启策略不等于健康故障自动重启，宿主重启时也不能假定 depends_on 顺序被 daemon 强制遵循；Xray 业务只有本机代理路径，代理初始化与内核阻断必须实测。

人工审核 Compose 合并结果应为：vpn 有回环 8787/7928 和公网 TCP 443→8443；ingress 无 ports、无 cap_add/privileged，UID/GID 65532，共享 vpn 网络，挂载 runtime/ingress 只读。不得添加 host network、Docker socket、直连 outbound 或开放 7928。只在批准后由管理员在云安全组及现有宿主防火墙开放 **TCP 443**；不提供自动改防火墙脚本。

管理仍使用现有 SSH Tunnel，将客户端 localhost 端口映射服务器 127.0.0.1:8787（以及按需 7928），不要公网暴露管理后台。访问隐藏路径并登录，原有认证不变。

## 3. Shadowrocket 导入

- 私密传送 `secrets/exports/alice.vless.txt` 给 Alice；Bob 只能拿到自己的文件。文件含完整接入凭据，不通过公共订阅、在线二维码或公开仓库传送。
- iPhone Shadowrocket 从剪贴板导入 `vless://` 链接；核对服务器 IPv4、443、VLESS、TCP、Reality、Vision、SNI、chrome 指纹、pbk、sid。关闭 UDP 转发/Mux。客户端版本解析失败时按上述字段手工填写，不能降级为无加密连接。
- 选择全局代理模式进行验收，关闭绕过规则及自动 DIRECT 回退。业务 DNS 使用通过代理的 DoH，服务器地址使用 IPv4，避免代理域名引导解析。按客户端版本确认 DNS 设置的实际行为，并在客户端侧做 DNS 抓包；服务端不能控制客户端绕过代理的流量。
- 可选二维码：管理员在本地安装可信 qrencode 后，在私密终端执行下列命令；不把 PNG 或终端二维码上传。二维码容量和应用识别需要实测。

```bash
umask 077
qrencode -o secrets/exports/alice.qr.png < secrets/exports/alice.vless.txt
```

工具只清理自身生成的 vless/clash 文件；二维码、密码管理器备份和朋友保存的副本需手动清理。撤销是否生效取决于服务器用户配置更新，不依赖销毁所有客户端副本。

## 4. Clash Verge 导入

将个人 `alice.clash.yaml` 作为本地配置导入使用 Mihomo 的 Clash Verge。文件是 YAML 兼容的 JSON；选择 VPN 组里的 Alice 节点，打开系统代理，按需要启用客户端 TUN。配置只含该用户、无 DIRECT 回退，UDP 显式 REJECT，IPv6 关闭；DNS 使用 fake-ip 和指定经过该节点的 DoH（带 `#节点名`）。核对当前 Mihomo 支持该语法，配置校验和实际 DNS 抓包必做。

不要合并进含直连 fallback、绕过规则或自动订阅覆盖的配置做安全验收。应用不遵循系统代理、IPv6、其他 VPN、客户端局域网 DNS 都可能旁路，需客户端侧另行约束。两款客户端都不会在原 TCP 会话断开后保持同一条业务 TCP；应自动重试建立新连接，无需重新导入。

## 5. 用户新增、禁用、删除与轮换

变更采用维护窗口中的显式事务。**先停止 ingress，再修改数据库、render、Xray test，最后重建 ingress**；任何中间步骤失败保持停止。仅执行 add/disable/delete 不会热更新正在运行的 Xray。禁止跳过 stop，否则已建立会话不会立即撤销。此设计用所有用户短暂重连换取明确的旧会话失效，不影响 VPNGate 控制连接。

```bash
docker compose -f compose.yaml -f compose.v1.1.yaml stop ingress
python3 scripts/ingress_users.py disable alice
python3 scripts/ingress_users.py render
docker compose -f compose.yaml -f compose.v1.1.yaml run --rm --no-deps ingress run -test -config /run/ingress/server.json >/dev/null 2>&1
docker compose -f compose.yaml -f compose.v1.1.yaml up -d --force-recreate ingress
```

- 新增：将 disable 替换为 `add charlie`，成功后 `export charlie`，仅交付 Charlie 文件。
- 禁用：`disable alice`，保留状态用于审计/恢复；导出被拒绝，服务器不包含该 UUID。
- 删除：`delete alice`，数据库移除；同名重新 add 生成新 UUID，不复用旧凭据。
- 恢复：`enable alice`，保留原 UUID；泄露后不要 enable，应 delete/add 轮换。
- 列表：`list` 仅输出用户名/状态；`export alice` 只写私密文件，不打印链接。
- Reality 私钥泄露：停止入口，在管理员控制下备份/移走旧数据库并重新 init/add/render，重新分发所有用户配置，旧导出全部作废。
- 内部代理密码轮换：保持 ingress 停止，按 V1.0 流程替换凭据/重建 vpn，重新 render 并重建 ingress；不能让 server.json 残留旧密码。

VPN 容器被 recreate 后必须同时 force-recreate ingress，避免 sidecar 仍引用旧网络命名空间；计划重启也协调两者。宿主重启恢复测试必须在批准的维护窗口执行。配置与数据库持久化，客户端凭据不因重启改变。`unless-stopped` 不自动恢复人为停止的服务。

## 6. 真实防泄漏验收（全部必做，health 仅辅助）

准备外部受控 HTTPS 测试服务器 A（与本宿主、VPNGate 节点、Reality 目标不同），记录其固定公共 IPv4、端口和请求日志；另准备域名 B 指向 A 和受控 DNS 查询记录。A 持续记录看到的源 IP。客户端开启全代理、关闭 DIRECT 回退，用唯一**非敏感**测试编号和禁缓存请求区分每次尝试。

记录宿主原生公网 IP S、VPNGate 出口 IP V、客户端直接出口 C，三者必须可区分。测试包含每秒新 HTTPS 请求、长下载/长 TCP 会话、随机子域 DNS 请求。抓包保存在管理员私密的项目内 runtime 验收目录，不提交 Git；包可能含业务与认证元数据，不上传。

由管理员找到 vpn 容器网络命名空间，用受控抓包工具同时观测：

- 容器 **eth0** 到 A 的 IPv4/IPv6、TCP/UDP、DNS（特别是 B），以及 tun 上的对应流量。
- 宿主真实公网网卡，到 A 的出站；结合受控 A 的源 IP 日志，排除 Docker NAT 误判。
- 客户端侧网卡的 DNS/DoH 与业务目的，确认无 C 直连目标；加密客户端→服务器 443 及 OpenVPN 外层连接属于正常流量。

不要把所有 eth0 包当作泄漏，也不要只找明文 HTTP：直连 TLS 到 A 同样是泄漏。允许列表仅为客户端加密入站回复、VPNGate API/控制面、OpenVPN 外层等已解释连接；Reality 目标连接应仅见 tun，不能见 eth0 原生直连。对 A 及 B 的判定不能仅靠宽泛控制面过滤。

| 场景 | 人工故障注入/操作 | 必须观察到的结果 |
| --- | --- | --- |
| 正常、多用户 | Alice、Bob 各连接并请求 A/B | A 看到 V，绝不是 S/C；两人均可用；eth0 无到 A 或业务 DNS 的原生流量 |
| 凭据隔离 | 错 UUID、撤销 Alice、交叉 short ID/UUID 测试 | 错/撤销 UUID 无业务；Bob 重连后成功；short ID 非身份绑定不能单独充当隔离证据 |
| 未连接启动 | 无已就绪 tun 时启动/重启入口 | 无业务成功；握手可失败；无原生出口流量 |
| VPN 断线 | 后台断开；并另测管理员终止活动 OpenVPN 子进程 | 新请求失败、长流停止，无到 A 的 eth0 包、A 无源 S 请求 |
| 强制维持故障 | 容器范围暂时阻断已记录的 OpenVPN 外层目标，持续至少 60 秒 | 防止自动重连掩盖断线；全窗口禁止原生出口，业务和 DNS 均失败 |
| tun 消失 | 在容器内删除**实际**活动 tun，不假定 tun0 | 新旧连接无泄漏；身份/心跳撤销；不得因同名重建复用旧 socket |
| 路由失效 | 容器内删除 mark 规则、清空 table 100，分别测试；不改主路由 | 即使 main 指向 eth0，带绑定/标记业务也不从 eth0 发出；入口不可用 |
| Kill Switch 未就绪 | 容器内移除 public_vpn_node 表，另测 public_vpn_ingress 表缺失 | 新连接被运行时校验拒绝，监视器关闭已有 socket；原有 socket 仍绑定 tun；禁止同时解除所有安全层 |
| Xray 无直连权限 | 使用同镜像/UID 的无秘密测试配置，尝试直连 A、DNS、IPv6、8787 | UID DROP 计数增长，无成功直连；不能仅看生产配置没有 freedom |
| Reality 未认证握手 | 对 443 发普通 TLS/错误 short ID；VPN 正常与断线都测 | 只可转发固定目标且经 tun；故障时目标不可达，无 eth0 直连目标 |
| 节点切换 | 后台改节点，记录旧/新 tun 名和 ifindex | 旧连接终止；新请求只见新出口 V2；客户端不改配置 |
| 自动重连 | 撤销临时故障，等待维护逻辑重连 | 同一客户端配置自动恢复，A 看到恢复后的 V2；不人工重新导入 |
| 服务/服务器重启 | 获批窗口重启本项目、宿主；不重启其他服务 | 自动恢复；入口先关闭后恢复，两个容器同网络命名空间，凭据不变 |
| 边界端口 | 从真实外网探测 IPv4/IPv6 8787、7928、9443、8443、443 | 只有预期 TCP 443 可接入；8787/7928 只经本机/SSH，UDP 不可用 |

故障命令必须由管理员根据现场活动 PID、tun、命名空间构造，限定本项目容器；不复制未知 PID 或直接操作宿主路由/防火墙。本页不自动执行故障注入。每次记录注入/恢复时间，检查抓包丢包统计，至少覆盖故障持续 60 秒及恢复 60 秒；若故障早已自动恢复，不能算断线验收成功。恢复规则先使用完整关闭门，再恢复路由和 tun 校验；最稳妥的是按维护流程重建本项目两个容器，重新验收。

**判失败：** A 收到源 S 的任何测试业务，或 eth0/宿主公网网卡出现到 A/B 的非隧道业务/DNS，或任一撤销用户旧会话仍能发送业务，或客户端回退 C 直连。发现即保持入口停止，保留私密证据，修复后全套重测。healthy、浏览器显示“连接失败”、curl 非零退出码均不能单独证明安全。

验收记录应包含日期、版本/digest、S/V/C、tun/ifindex、mark/table/nft 读回、两个用户结果、每类故障时间线、包计数/丢包统计、A 侧源 IP、恢复耗时、验收人及未通过项；不要记录 UUID/密钥/导入 URI。

## 7. 已知限制与回滚

离线测试只能证明生成逻辑/模拟失败分支；当前环境的真实验收范围见页首。新环境的 nft JSON 格式、目标站握手和客户端行为仍需重新验证，Mihomo DNS 语法及客户端行为不由 Shadowrocket 验收代替。严格读回遇到不支持格式会拒绝启动，不能为上线临时绕过。新连接检查包含子进程开销，共用 64 个原代理连接槽，固定目标转发最多 32 个，朋友数量和性能需要实测。

Reality 目标仍有可用性/第三方信任及未认证固定转发滥用风险；公网入口存在 DoS 面，没有完整每用户限速/配额；日志关闭减少诊断信息。规则与本机代理不能防御宿主管理员、内核、Docker 或 VPN 特权控制进程被攻陷。shared network namespace 的生命周期必须运维协调。

回滚：管理员停止并移除 ingress 服务，只用原 compose.yaml 重建 vpn、恢复审核过的 V1.0 镜像；确认公网 443 映射消失、8787/7928 仍回环。不要 down -v，不删数据或其他服务，不沿用旧网络命名空间，不执行全局 prune。回滚后的公网用户不可用属预期；原 V1 本机/SSH 功能应重新测试。

以下为先前修复记录，不表示当前仍待部署；当前发布状态见页首。

本次离线审查确认旧 ingress guard 读回验证把 `ct state established` 固定为

## 8. 新服务器恢复

`secrets/ingress.json` 是含服务器 Reality 密钥及用户凭据的 ingress state，**不进入 Git**。仓库、镜像和公开 examples 均不能恢复这些秘密；不要将运行时 UUID、Reality key、shortId 或 VLESS URI 写入仓库。

1. 恢复公开代码，运行离线 verify 与 Xray pin 检查，使用上述正式镜像精确 digest。部署时显式配置 `REALITY_TARGET`，先做 TLS 1.3 兼容性验证，再验证实际 Reality 握手。`www.apple.com` 仅为本次已验证示例。
2. 没有独立安全备份时，由管理员在新服务器重新 `init` / `add` / `render`（命令见第 2 节）。内部代理凭据也需安全配置。重新生成会改变密钥和用户凭据，必须重新 export 并私密分发客户端配置，旧配置不可继续使用。
3. 有独立安全备份时，由管理员从离线加密备份或受控秘密存储恢复 ingress state 和所需内部代理凭据，目录 0700、秘密文件 0600；按新服务器地址检查 state 并重新 render，按需重新 export。不要通过 Git、公开附件或日志传递备份。
4. 无论采用哪条路径，`REALITY_TARGET` **必须与 ingress state 的 `sni` 一致**，客户端 SNI 同步。不能只改环境变量而沿用旧 state / server.json / 客户端导出；调整目标需管理员协调重新 render、export 及维护窗口部署。禁止用示例占位值启动。
5. render 生成的运行配置仍是秘密，按第 2 节设置挂载权限。重新检查 TCP 443、管理端口回环、Kill Switch、断线 fail-closed 与自动恢复；客户端 UDP forwarding 保持关闭。服务重启恢复不等于新服务器无需初始化，也不等于已验证宿主整机重启。
