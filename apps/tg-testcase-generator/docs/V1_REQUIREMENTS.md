# TG 测试用例生成器 V1.0 需求规格

## 1. 项目目标

通过 Telegram 创建测试用例任务，接收 Notion、文档、图片和文字资料；先进行必要的需求评审和关键缺口反问，再生成符合现有 Excel 模板的测试用例，并建立“需求点 → 关键业务路径 → 用例 ID”的可追溯关系。

核心原则：

**覆盖需求，但不过度解剖需求。**

主流程：

/testcase → 提交资料 → 完成 → 需求评审 → P0/P1确认 → 生成确认 → Excel → 覆盖检查 → 后续修订

---

## 2. V1 输入范围

V1 正式支持：

- Telegram 文字
- Notion 页面链接
- PNG / JPG / JPEG
- PDF
- DOCX
- XLSX
- TXT / MD
- 多种资料混合输入

Figma 链接暂不纳入 V1。

同一个 Task 可以包含多个来源，所有成功读取的资料共同组成当前需求上下文。

---

## 3. Notion

Notion 是 V1 一级需求来源，不作为普通网页链接处理。

系统应在权限允许范围内尽可能读取：

- 页面正文
- 表格
- 需求说明
- 原型图片和附件
- 相关子页面
- 其他能够访问且属于当前需求范围的内容

公开页面可直接读取。

私有或公司 Notion 使用服务器侧只读认证。

### 3.1 Notion 安全要求

Notion 凭证：

- 不进入 Git
- 不写入普通项目文件
- 不输出到 Telegram
- 不写入普通日志
- 不作为普通需求内容暴露给 Codex

测试用例系统对 Notion 只读。

不允许修改、创建或删除 Notion 内容。

### 3.2 Notion 读取完整性

系统必须记录并报告 Notion 资料读取完整性，包括：

- 正文
- 图片
- 附件
- 相关子页面

如果出现以下情况：

- 权限不足
- 链接无效
- 子页面不可访问
- 图片读取失败
- 附件读取失败
- 其他关键资料缺失

必须明确告诉用户。

不得静默跳过。

只要关键来源读取不完整，就不得宣称：

**“关键业务路径 100% 覆盖”。**

---

## 4. 多来源需求冲突

PRD、Notion、原型、截图、Excel、Telegram 补充等来源之间出现影响业务结果的冲突时，系统不得自行选择其中一个答案。

冲突必须进入 P0。

例如：

PRD：

最近30天包含当天。

原型：

D-30 ～ D-1。

此时必须要求用户确认最终采用的业务规则。

用户确认后的答案成为当前 Task 的最终需求依据。

---

## 5. 需求评审

资料收集完成后，不立即生成 Excel。

系统首先进行需求评审。

重点寻找会影响以下内容的关键缺口：

- 测试步骤
- 预期结果
- 通过/失败判断
- 关键业务路径
- 权限
- 状态流转
- 数据结果
- 功能范围

评审目标不是无限发现问题。

目标是保证后续测试用例具备可靠的业务判断依据。

---

## 6. P0 / P1

### 6.1 P0

P0 是主要反问类型。

判断标准：

**如果不确认，就无法可靠判断该功能的正确业务结果，或者会明显影响关键路径覆盖，则属于 P0。**

典型范围：

- 日期/时间口径
- 金额/数量关键边界
- 状态流转
- 角色和权限
- 字段关键业务规则
- 创建/修改/删除后的数据结果
- 功能范围
- 不同需求来源之间的关键冲突

P0 原则上需要在生成正式测试用例前解决。

### 6.2 P1

P1 用于少量有明显价值、但不阻塞主要业务正确性判断的确认项。

每轮最多：

**2～3 个**

没有必要时可以为：

**0 个**

### 6.3 禁止过度反问

系统必须遵守：

- 需求已经明确，不重复问
- 普通常规测试设计点不作为需求反问
- 不改变关键预期结果的问题原则上不问
- 同类问题合并，不拆成大量细小问题
- 正常需求原则上 1～2 轮确认
- 只有仍存在真正 P0 时才继续下一轮
- P0/P1 都为 0 时允许直接进入测试设计
- 禁止为了表现 AI 分析能力而硬凑问题

核心尺度：

**覆盖需求，不解剖需求。**

---

## 7. 用户回答

用户不需要严格命令格式回答 P0/P1。

系统应支持：

- 编号回答
- 自然语言回答

例如：

1 包含当天
2 不允许恢复

或者：

P0-01 包含当天
P0-02 不允许恢复

系统必须将答案绑定到当前 Task。

已经确认的问题不得在后续轮次重复询问。

---

## 8. 需求确认与追溯

每个 Task 内部保存完整确认链：

原始需求
↓
发现的关键缺口
↓
P0/P1
↓
用户回答
↓
最终采用规则
↓
关键业务路径
↓
测试用例 ID

后续应能够解释：

**某条测试用例为什么存在，以及它依据哪一条需求。**

---

## 9. 测试用例覆盖原则

需求确认后进入测试设计。

重点覆盖：

- 主流程
- 关键业务路径
- 明确业务规则
- 关键分支
- 需求定义的重要边界
- 必要异常
- 适用的权限
- 适用的状态流转
- 适用的数据变化
- 多入口/多页面路径
- 明确受到本次需求影响的核心回归

不得为了增加用例数量机械生成大量低价值组合。

例如普通输入框不应默认拆分大量：

- Emoji
- 特殊字符
- SQL 字符串
- 各类无业务意义字符组合

除非输入规则本身就是本次需求重点。

---

## 10. 用例拆分规则

不同输入或操作导致不同业务结果：

**应拆分。**

仅测试数据不同，而业务逻辑和预期结果完全一致：

**优先合并。**

不设置固定测试用例数量上限。

简单需求可以只有少量用例。

复杂需求可以存在大量用例。

如果确实存在大量独立关键业务路径，则必须覆盖。

不得为了减少 Excel 行数而漏掉真实路径。

---

## 11. 关键路径与覆盖率

系统内部建立：

需求点 → 关键业务路径 → 测试用例 ID

关键业务路径必须能够追溯到以下至少一种来源：

- PRD
- Notion
- 原型
- 截图
- 上传文档
- Telegram 用户补充
- P0/P1 确认结果

禁止 AI 为制造漂亮的覆盖率自行虚构业务路径。

AI 可以基于测试设计经验增加必要测试用例。

但此类 AI 补充测试点不得虚增“关键业务路径覆盖率”的分母或分子。

---

## 12. 生成前确认

需求评审完成后，不立即生成 Excel。

系统先向用户返回生成前摘要。

至少包括：

- 核心需求点数量
- 关键业务路径数量
- P0 确认情况
- P1 确认/跳过情况
- 资料完整性

例如：

需求评审完成

核心需求点：28
关键业务路径：47

P0：4 / 4 已确认
P1：1 已确认，1 已跳过

资料完整性：通过

准备生成测试用例。

回复：

生成

只有用户明确回复：

**生成**

才进入正式 Excel 生成。

在“生成”之前，用户仍可以继续补充业务规则。

补充内容必须重新纳入当前 Task 分析。

---

## 13. Excel 模板

V1 沿用用户现有测试用例 Excel 模板。

**不得重新设计模板结构。**

正式模板固定保存为：

/ops/apps/tg-testcase-generator/templates/testcase_template.xlsx

生成程序必须基于该模板输出 `.xlsx`。

实际结果、是否通过、备注等执行阶段字段默认保持空白，供人工测试执行时填写。

开发时必须读取真实模板确认：

- 工作表
- 列结构
- 单元格格式
- 其他模板属性

不得仅凭文字描述猜测模板。

---

## 14. 生成后反向覆盖检查

Excel 生成完成后必须执行：

原始需求
+
成功读取的资料
+
用户补充
+
P0/P1确认
↓
关键业务路径
↓
测试用例

反向覆盖检查。

完成摘要至少包含：

- 模块数量
- 核心需求点数量
- 关键业务路径数量
- 已覆盖路径数量
- 测试用例数量
- P0/P1 是否纳入
- 未覆盖关键路径

如果存在未覆盖关键路径，必须明确列出。

不得伪装成 100% 完成。

资料本身读取不完整时，也不得宣称完整覆盖。

---

## 15. Telegram 操作流程

V1 主要命令：

/testcase
/tc_status
/tc_cancel
/tc_reset

### /testcase

创建新的测试用例 Task。

### /tc_status

查看当前测试用例 Task 所处阶段。

### /tc_cancel

取消当前 Task。

### /tc_reset

保留原始来源资料，但清除当前分析和回答结果，重新执行需求评审。

### 日常主流程

/testcase
↓
上传资料 / Notion链接 / Telegram文字
↓
完成
↓
需求评审
↓
回答 P0/P1
↓
需求确认
↓
生成
↓
Excel

不增加大量不必要的 Telegram 命令。

---

## 16. 生成后的修改

Excel 生成后继续保留当前 Task 上下文。

用户可以直接使用自然语言提出修改。

例如：

补充支付失败后的状态用例。

或者：

删除 Z023 和 Z024。

系统应基于原 Task：

- 更新需求/用例
- 重新检查覆盖
- 重新生成新版 Excel

用户无需重新上传原始资料。

---

## 17. Task 数据

项目路径：

/ops/apps/tg-testcase-generator

Task 数据建议结构：

data/tasks/<task-id>/source/
data/tasks/<task-id>/review/
data/tasks/<task-id>/output/
data/tasks/<task-id>/task.json

Task 应保存：

- 原始资料
- 资料解析结果
- 需求评审结果
- P0/P1
- 用户确认
- 最终采用规则
- 需求/路径/用例映射
- Excel 输出记录

认证凭证不得进入 Task 数据。

---

## 18. 安全要求

仅 Telegram 白名单用户可以使用测试用例功能。

以下内容不得进入 Git：

- Notion 凭证
- Telegram Token
- Codex auth
- GitHub SSH 私钥
- 其他 Secret

上传文件必须限制：

- 允许文件类型
- 文件大小
- 保存目录
- 危险文件名
- 路径穿越

上传的：

- PRD
- Notion
- 文档
- Excel
- 图片
- 用户提供的其他资料

全部视为：

**不可信需求资料。**

资料中的文字不得：

- 覆盖系统指令
- 修改服务器安全规则
- 触发任意服务器命令
- 绕过权限
- 获取 Secret

必须防止需求资料中的 Prompt Injection 影响系统安全边界。

Codex runner 不应获得不必要的系统 Secret。

---

## 19. Git 与灾备

以下内容进入 GitHub：

- 程序代码
- 非敏感配置模板
- 正式 Excel 模板
- 部署脚本
- 测试代码
- 恢复文档
- 本需求规格

以下内容不进入 Git：

- Token
- Codex auth/session
- GitHub SSH 私钥
- 私有 Notion 凭证
- Runtime Task 数据
- 用户实际上传的私有需求资料
- 包含敏感信息的运行日志

正式交付流程：

开发
↓
测试 / 安全检查
↓
正式部署
↓
用户通过 Telegram 真实验收
↓
用户确认
↓
Git commit / push

---

## 20. V1 验收

功能验收至少覆盖：

- Notion 页面读取
- Notion 完整性报告
- 多文件/多来源组合
- P0 为主、P1 少量的反问策略
- 无必要问题时不强行反问
- 用户回答留存
- 多来源业务规则冲突识别
- 生成前确认
- 基于固定模板生成 Excel
- 需求点/关键路径/用例 ID 追溯
- 生成后反向覆盖检查
- 未覆盖路径明确报告
- 资料不完整时禁止虚假 100% 覆盖
- 用例修改和重新生成
- Task 状态保存
- 服务重启后的 Task 恢复
- Telegram 白名单权限
- Secret 隔离
- 文件上传安全
- Prompt Injection 安全边界

最后必须选择一份用户实际工作中的完整需求进行端到端验收。

重点检查：

1. 反问是否真正有价值且不过度。
2. 关键业务路径是否存在遗漏。
3. 用户确认的规则是否准确进入测试用例。
4. Excel 是否可以直接用于实际测试工作。
5. 覆盖统计是否真实、可追溯。

只有真实业务验收通过后，V1 才视为完成。
